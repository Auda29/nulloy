# Upstream #255: stabilize the trash return contract

## Scope and live premise

Reviewed [#255](https://github.com/nulloy/nulloy/issues/255) on 2026-09-08:
macOS 15.5 crashes when selecting the next track after trashing a track. The live
issue declares zero comments; the paginated comments endpoint returned zero.
Upstream PR searches (`#255`, all states; `trash`, open; `delete crash`, open)
all returned empty lists. `gh issue view --comments` hit an old Projects GraphQL
error, so the issue and full comment list were read through the REST API instead.

This is **shared-contract stabilization, not a claim to fix the original macOS
crash**. The fork already ported PR #263's item-lifetime improvements. No playlist,
playback, skin or top-level build configuration changes are made here.

Baseline: `027d81a583b07457a4fa5f18b3e7dcca50b05b58`.
`actionManager.cpp` calls `removeFiles(deleted)` with `moveToTrash()`'s return.
The old implementation instead returned failed/unattempted paths. Its history
shows this residual-list behavior since 2017, with confirmation added in
`b62c3fe` (2024); preserving confirmations is intentional, not a reason to retain
the contradictory result. There is one production caller. The existing
`removeFiles()` matches every playlist row by path, including duplicate rows.

## Contract and changes

- Return unique paths actually reported successful by the native trash adapter
  or successfully removed by `QFile::remove()` after explicit confirmation.
- Preserve input order; process identical path strings once. Do not canonicalize
  paths or resolve symlinks as part of this change.
- Cancel before the first operation: empty result. Cancel or error after some
  successes: those successes only. Failed and unattempted paths are not returned.
- A trash failure still offers permanent deletion with **Cancel as the default**.
  Disabling ordinary trash confirmation does not disable this safeguard.
- Preserve the checkbox preference: opt-out takes effect only after Yes.
- Windows: `fAnyOperationsAborted` is cancellation, independently of the shell
  return code. Stop the batch with earlier successes and **never offer permanent
  deletion after native cancellation**, including declining the unrecyclable-file
  warning. The first revision incorrectly routed cancellation through the error
  fallback; this review correction supersedes that interpretation.
- `NativeResult` carries the native error code and cancellation boolean separately;
  there is no numeric cancellation sentinel. All three adapters share its declared
  signature. Linux's `-1` remains an error, and macOS native status codes remain
  unchanged (this correction does not redesign the macOS adapter).
- Windows requests `FOF_WANTNUKEWARNING`, so `FOF_NOCONFIRMATION` cannot silently
  authorize permanent deletion when recycling is unavailable. This is a deletion
  safeguard, not a redesign of the application's dialogs.

Microsoft documents both the [zero-return cancellation caveat](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/nf-shellapi-shfileoperationw)
and [FOF_WANTNUKEWARNING's override of FOF_NOCONFIRMATION](https://learn.microsoft.com/en-us/windows/win32/api/shellapi/ns-shellapi-shfileopstructw).

## Runtime evidence and TDD

Standalone harness: `tests/upstream/255/CMakeLists.txt`.
`testTrash` compiles the **real production trash.cpp and settings.cpp** and drives
real modal Qt message boxes. Only `_trash` and the settings storage path are
controlled boundaries. Successful simulated trash operations really rename
freshly generated files within a `QTemporaryDir`; permanent deletion uses the
real production `QFile::remove`. No user media, user settings or system trash is
used. Failure cases include a generated nonempty directory and a never-created
path; they do not rely on permissions that behave differently under root.

`testWindowsTrash` compiles the **real production trash_win.cpp, trash.cpp and
settings.cpp** on Linux against
small test-only Windows declarations. The controlled `SHFileOperation` boundary
varies the return code and abort flag independently and checks the UTF-16 double
terminator (including Unicode and spaces). This proves adapter logic, **not**
Windows SDK/ABI correctness or real Recycle Bin behavior. The declarations are
private to that test target and never enter the player build.

Observed RED -> GREEN, each before its corresponding production change:

| Regression | RED | GREEN |
| --- | --- | --- |
| Complete success | Returned zero paths instead of two | Both moved paths returned |
| First/later confirmation cancellation | Returned input list instead of earlier successes | Both data rows passed |
| Duplicate path | Tried the first file again and stopped on an error dialog | Each unique path tried once; later file moved |
| Windows zero return with abort (initial revision) | Incorrectly returned success | Source retained; cancellation result refined below |
| Windows irreversible-delete warning | Missing `FOF_WANTNUKEWARNING` | Flag present with undo and normal-confirmation flags retained |

Additional regression/characterization rows cover total and partial trash error,
permanent-delete decline/accept, failed permanent deletion, missing paths, empty
