# Upstream #255: trash results and Windows recycle-bin safety

## Current behavior

The shared loop returns only paths successfully recycled or explicitly permanently deleted. Cancelled, failed and unattempted paths stay in the playlist. Duplicate path strings are attempted once. Permanent deletion still requires its own confirmation, with Cancel as the default.

The Windows adapter now uses `QFile::moveToTrash()` on the fork's supported Qt 5.15 / Qt 6 and Windows 10+ builds. Qt's Windows implementation uses `IFileOperation` and refuses deletion when recycling is unavailable. The adapter also requires the original path to disappear before reporting success. A failed recycle reaches the existing explicit permanent-delete question. Qt does not open a separate native confirmation dialog.

Sources: [Qt 6 implementation](https://github.com/qt/qtbase/blob/6.11/src/corelib/io/qfilesystemengine_win.cpp), [Qt 5.15 implementation](https://github.com/qt/qtbase/blob/5.15/src/corelib/io/qfilesystemengine_win.cpp), [Microsoft operation flags](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-setoperationflags).

Linux and macOS adapters retain their existing result/cancellation contract. This does not establish a fix for the original [macOS 15.5 crash](https://github.com/nulloy/nulloy/issues/255) after trashing a track.

## Windows acceptance finding, 9 September 2026

The combined test package exposed a real safety defect in the previous Windows adapter:

- The tested NTFS volume D: already had `NukeOnDelete=1`. Its Windows setting bypasses the recycle bin. No setting was changed for the test.
- Confirming the player's ordinary trash question silently deleted generated test tones 1 and 2. Neither their metadata nor their payload appeared in the Windows recycle bin.
- Removing `FOF_NOCONFIRMATION` alone did not fix the problem. Generated tone 3 was also deleted without a permanent-delete warning.
- The Qt-based adapter preserved generated tone 4 and opened the explicit `Do you want to delete permanently?` question. Cancel preserved both the file and its playlist row.
- Before the adapter replacement, ordinary cancellation and partial-batch cancellation correctly preserved failed/unattempted paths. That shared-loop behavior is also covered by automated tests.

Only disposable generated tones were deleted. No user music was used for deletion tests. The old mock assertion that `FOF_WANTNUKEWARNING` guaranteed a warning was insufficient evidence and has been replaced by real Windows filesystem tests.

## Tests

`testTrash` compiles production `trash.cpp` and `settings.cpp`, exercises real Qt dialogs, and substitutes only the native operation and settings location. It covers complete/partial success, duplicate paths, ordinary confirmation cancellation, errors, permanent-delete decline/accept/failure and preference persistence. Its eight shared-boundary native-cancellation rows inject `NativeResult::cancelled=true` on the first or a later file, with zero/nonzero error codes and ordinary confirmation enabled/disabled. They verify only earlier successes are returned, later files are not attempted, cancelled/unattempted bytes are preserved, and no permanent-delete fallback is offered. This tests the shared cancellation contract, not native OS cancellation UI; the current Windows adapter always returns `cancelled=false`.

The opt-in `testWindowsTrash` compiles the current production Windows adapter. It creates uniquely named temporary Unicode files under an explicitly selected directory and checks:

- Recycling disabled: an error is returned and the original bytes remain intact.
- Recycling enabled: the original disappears, its actual `$I` metadata is present and the matching `$R` payload has identical bytes.
- A missing file returns an error.

The successful tiny test payload remains in the recycle bin for inspection. No unrelated recycle-bin entries are changed. The old Linux mock of `SHFileOperation` no longer describes the current adapter and is no longer built.

Previously reported with Qt 6.11.2 and Qt 5.15.19, GCC 16.2.0 on Windows 11 (not rerun as part of this Linux shared-contract review fix):

| Case | Qt 6 | Qt 5 |
| --- | --- | --- |
| D:, recycling bypassed, shared contract plus native test | 2/2 CTests passed | 2/2 CTests passed |
| E:, recycling enabled, metadata and payload verified | 1/1 CTest passed | 1/1 CTest passed |

For each toolkit, select its `QT_DIR` when configuring:

```powershell
cmake -S tests/upstream/255 -B build/trash-native -G Ninja -DNULLOY_NATIVE_TRASH_TESTS=ON
cmake --build build/trash-native
$env:NULLOY_TRASH_TEST_ROOT = 'D:/existing/disposable-test-directory'
$env:NULLOY_TRASH_EXPECT_RECYCLE = '0' # 0: existing bypass setting; 1: working bin
ctest --test-dir build/trash-native --output-on-failure
```

Set the expectation to the volume's actual behavior. Do not change system settings merely to make the test pass. Native tests are opt-in; ordinary component CI still runs the shared contract without touching the system recycle bin.
