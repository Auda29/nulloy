# Upstream #211: multiple external file-open messages

## Scope and evidence

[Upstream #211](https://github.com/nulloy/nulloy/issues/211) reports Windows 11
Explorer Enter on several selected songs: only the last song survives when
EnqueueFiles is off, only the last song starts when PlayEnqueued is on, and the
playlist index is repeatedly 1. The live issue has zero comments (all zero
retrieved). Related threads #95 (unwanted restart), #155 (enqueue/play preference
semantics), and #143 (folder-open feature, not this bug) were read in full.
Searches of upstream PRs for `#211`, `multiple files`, and `enqueue` found no
matching existing PR. The fork search for `211` also found none.

Baseline: `027d81a`. `NPlayer::readMessage()` applies replace/append and play
selection separately for every IPC message; `main.cpp` calls the same slot for
the startup arguments. `addFiles()` and `setFiles()` already update track indices.
A multi-path message or multi-file drop does not reproduce the repeated-message
problem. History supports selecting the first new row: upstream commit
`39b9897eba1d30a358f3091e2734d4583186bd05` is explicitly titled "play first enqueued
file from cli"; `502d5d95cc59dc2e53b947a759797069ee6e9bb7` introduced PlayEnqueued.
No changes to drop handling, skins, resume features (#98/#23), registry
associations, or the IPC wire format belong in this fix.

## Acceptance contract

- A short external-open burst preserves received message order and path order
  within each message. The first message applies existing preferences immediately;
  continuations append without clearing or repeatedly selecting playback.
- EnqueueFiles=false replaces once and plays the first new row, regardless of
  PlayEnqueued. EnqueueFiles=true retains the old list; if stopped or
  PlayEnqueued=true it starts at the first new row, otherwise it preserves current
  playing/paused media and position. This includes a restored startup playlist.
- Commands `--next`, `--prev`, `--stop`, `--pause` keep their original priority and
  immediate execution; they terminate the current burst. No deferred file-open
  callback may restart playback after a command.
- Empty activation and nonexistent paths must not clear the playlist. Preferences
  changing between file messages must not reuse an incompatible burst decision.
- Bursts must have an idle boundary and a non-sliding maximum lifetime. Receipt
  after either boundary is a fresh open, not an unbounded append session.
- Assert row order, playing row, and actual `%i` display values using production
  player/playlist code; exercise separate processes over QtSingleApplication IPC.

## Implemented policy and trade-offs

`NFileOpenBurst` uses monotonic elapsed time, a **250 ms idle gap**, and a
**1000 ms maximum age measured from the first accepted file message**. Both
comparisons are strict (`<`): receipt at or beyond either boundary is a new open.
The first message executes synchronously; later messages within both bounds only
append. There is no pending file buffer, timer callback, delayed startup decision,
or queued playback to undo a later command. Settings changes and recognized CLI
commands terminate the old grouping decision. Empty/nonexistent messages neither
clear nor extend it. Within-message order, message receipt order and duplicate
paths are not sorted or deduplicated.

These constants are a bounded interaction policy, **not a Windows timing
contract**. They prevent a continuous stream from becoming an indefinitely sliding
append session, while allowing a modest short burst without delaying the first
open. Separate intentional opens inside the bounds can be grouped; a slow or
large Explorer selection, cold initialization, or a busy GUI that crosses either
bound can be split and replace an earlier group when EnqueueFiles is off. No
selection identity is available in the existing wire format to resolve that
ambiguity. A true arbitrary-size shell transaction needs an explicit selection
protocol/COM handler; increasing a debounce interval cannot supply that guarantee.
Native QFileOpenEvent handling and non-IPC UI operations remain unchanged.

The original `--pause` dispatch currently calls `play()`. This patch preserves
that existing mapping rather than silently fixing an unrelated command behavior.
`loadDefaultPlaylist()` and `main.cpp` are unchanged. In particular, the startup
file decision still observes the same synchronous engine state, not a later state
settled by an event-loop batching delay.

## Windows CI / manual acceptance plan

The existing `.github/workflows/windows-cmake.yml` builds Qt5 and Qt6 on
windows-2022 and already tests extracted packages. Parent integration should add
this issue-specific test target alongside that build, linked to `nulloy_core`,
using the existing test plugin deployment. Do not interpret the Linux-only native
harness or process spawning as a Windows Explorer test.

Microsoft's [verb selection model documentation](https://learn.microsoft.com/en-us/windows/win32/shell/how-to-employ-the-verb-selection-model)
explains that legacy verbs default to Document, COM verbs default to Player, and
legacy Player selection is still limited to 100 items. It does not give an
inter-process delivery deadline or guarantee Explorer selection order. A plain
command-line IPC message contains no shell selection ID or end-of-selection
marker. A timing-based grouping policy therefore cannot identify arbitrary
selections perfectly. The portable ZIP does not install associations: record the
actual user's association/verb, not an assumed registry configuration.

Remaining native acceptance must use a disposable Windows 11 profile/package and
real Explorer: select three uniquely named valid WAV files, press Enter, repeat
with the player closed and running, for every EnqueueFiles/PlayEnqueued setting
and stopped/playing/paused/restored state. Record selection focus, delivered order,
playlist paths, displayed indices, playing row, position and launch timing. Repeat
with a larger selection and cold plugin cache, then perform two deliberately
separate rapid opens and opens outside the documented boundaries. Verify immediate
CLI controls during the burst. Capture video/logs and perform an audible check.
Run interactive Explorer automation on a logged-in Windows desktop (self-hosted
runner or manual lab); ordinary QProcess tests alone cannot establish shell
selection grouping. No upstream issue is to be closed on Linux evidence alone.
