# Upstream #241 — preserve Unicode with a legacy selection

Issue: https://github.com/nulloy/nulloy/issues/241
Base: `027d81a583b07457a4fa5f18b3e7dcca50b05b58`.

## Contract and scope

Read the body and all three comments, including the maintainer's explanation of
Windows-1251 and commit `d7dbb75` (Unicode and manually selected encoding should
coexist). PR searches `#241`, `encoding`, `Cyrillic` found no matching open work.
Reviewed the fork's earlier Unicode fix `22b3ed0` and resource port PR #6.

The original attachment already reads correctly with Windows-1251 selected on
the baseline. Automatic detection of unspecified legacy encoding is not promised
or added. However, with that same selection the current reader corrupts real
UTF-8 and UTF-16 tags containing `Привет 日本語 🎵`. TagLib's Latin-1 conversion
truncates non-Latin-1 codepoints before the legacy heuristic runs.

The narrow fix bypasses legacy reinterpretation when `TagLib::String::isLatin1()`
is false. This preserves already-decoded Unicode without changing codec selection,
UI, valid legacy-byte recovery or default/UTF-8 behavior. All existing `toUnicode`
callers benefit (title/artist/album/comment and raw property values). Genre/BPM
already use TagLib's Unicode conversion and do not have this heuristic.

The old heuristic remains ambiguous for text entirely within Latin-1. This change
is not a universal encoding detector and does not claim to close every variant of
#241. Rollback is removal of the added `!tstr.isLatin1()` condition.

## Verification

```sh
cmake -S tests/upstream/241 -B build-issue241 -G Ninja
cmake --build build-issue241 -j1
ctest --test-dir build-issue241 --output-on-failure
# Optional local acceptance; never redistribute the downloaded audio:
NULLOY_ISSUE241_SAMPLE=/path/to/issue241-sample-0.mp3 build-issue241/testIssue241
```

The harness compiles the real production reader (no copied conversion function).
ffmpeg generates legal one-second sine MP3s; TagLib writes explicit UTF-8, UTF-16
or Latin-1-carried Windows-1251 ID3v2 frames. Title/artist/album and raw TITLE values
are checked. Empty/default, UTF-8 and unknown selections retain Unicode.

Baseline: two Unicode-under-Windows-1251 rows fail, other rows and original sample
pass. Fix: all nine Qt Test cases including setup/cleanup pass with the optional
original sample. Sabotage (remove only the new condition): the same two rows fail;
restoration passes. Without the external sample there is one explicit skip.

Local dependencies: Linux, Qt 6.8.2, TagLib 2.0.2. Qt 5/6-compatible harness and
production APIs are retained, but Windows/Qt 5 package execution is pending.
The standalone build emits pre-existing warnings for `AudioProperties::length()`
and `tagToKey`'s missing final return; these are outside the reproduced defect.

The original `example.zip` was supplied by the issue reporter and downloaded by
the audit worker. Only a local, read-only acceptance path is used here. No audio
from that attachment is committed or redistributed. Generated test metadata is
self-contained, and no user library files are written.
