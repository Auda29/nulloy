# Upstream #236: reachable window restoration

## Scope and evidence of the defect

Issue: <https://github.com/nulloy/nulloy/issues/236>. The live issue and its complete
one-comment thread were read on 2026-09-08. The reporter describes Windows 11
playing audio without a visible window; the maintainer asks about multiple monitors
and the saved `Position`. There is no confirmed reporter diagnosis. This change
fixes the demonstrated unreachable-coordinate class, not every possible cause of
an invisible application.

The upstream duplicate PR searches (`236`, `window monitor`, `invisible position`)
returned no candidates. The fork's issue-number search found merged PR #6 (the
GStreamer work), not a window-restoration implementation. The same keyword searches
found no open fork PRs. `docs/UPSTREAM_ISSUES_ANALYSIS.md`, C6, and the original
position-loading history were inspected: direct restoration was inherited, not an
intentional multi-monitor restriction.

## Behavior

- Preserve reachable saved positions and sizes, including negative coordinates,
  intentional partially offscreen placement, and windows spanning displays.
- Require a usable portion of the top strip, not merely a pixel of the window body:
  a 100-by-16 logical-pixel patch in the top 32 logical pixels. Thresholds shrink for
  windows/screens smaller than that patch. This is a conservative drag-area heuristic,
  not skin-specific hit testing or a UI redesign.
- If unreachable, center on the primary usable work area, reducing an oversized
  restored rectangle to that area. Skip temporarily invalid work areas; with none,
  leave geometry intact and wait for the next notification. Widgets' own minimum
  sizes still apply: on a display smaller than the UI minimum, recovery anchors its
  top at the work area rather than overriding the layout's minimum size.
- Use Qt logical coordinates directly; do not multiply coordinates by device pixel
  ratio or use a bounding rectangle that includes gaps between monitors.
- Check at settings load, explicit show, exit from maximize/fullscreen, and native
  restoration. Screen add/remove, primary changes, geometry/work-area changes queue
  checks after Qt updates its desktop information. New screens are observed while
  their pointers are valid; deferred callbacks never dereference a removed screen.
- While minimized/maximized/fullscreen, correct the cached normal rectangle without
  revealing or changing the window state. Native restore subsequently applies and
  clears that cache, so later moves are saved normally. Qt 5's legacy maximize work
  area lookup now uses the window's screen rather than always the primary display.
- Validate the length and conversion of saved coordinate/size lists. Invalid sizes
  use the existing 430-by-350 default. No settings format migration or UI changes.

### Reproduce

From the repository root (use an external build directory):

```sh
cmake -S tests/upstream/236 -B /tmp/nulloy-236 -DCMAKE_BUILD_TYPE=Release
cmake --build /tmp/nulloy-236 --parallel 1
ctest --test-dir /tmp/nulloy-236 --output-on-failure --timeout 180
QT_SCALE_FACTOR=1.5 xvfb-run -a -s '-screen 0 1600x1200x24' \
  /tmp/nulloy-236/testWindowRestoration
```

For this resource-constrained swarm, wrap configure/build/test commands in
`flock /home/hermes/workspace/nulloy-swarm/build.lock sh -c '...'` and allow up to
600 seconds including lock wait. Do not start another build after a tool timeout
until checking whether descendants are still running.

`-DNULLOY_QT_MAJOR=5` selects Qt 5 (Windows additionally requires WinExtras).
`-DN_SRC=/path/to/source-copy` supports testing original production files without
mutating the worktree. Windows test sources include the real `src/platform/w7TaskBar`
and required platform headers/libraries. The top-level Windows CMake is untouched.

## Remaining native acceptance (not claimed)

Qt 5 configuration was attempted but its development package is absent here.
Windows compilation, original-skin package execution, native taskbar behavior,
physical unplug/replug, per-monitor DPI, and decorated Windows frame metrics need
parent CI/manual verification. Xvfb has no window manager in this run; scaled Xvfb
is not proof of Windows mixed-DPI behavior. The parent owns independent review and
publication; this branch makes no upstream writes.

Use an isolated disposable profile and the current packaged application:

1. For Native, Metro, Silver, Slim, restore a reachable position/size; close/reopen,
   minimize/taskbar-restore, maximize/restore, fullscreen/restore. Preserve reachable
   normal geometry and maximize preference; verify subsequent user moves are saved.
2. Put the window on a secondary screen left of or above the primary. Close, unplug
   it, restart. Repeat with the app running while normal, hidden-to-tray, minimized,
   maximized, and fullscreen. Normal restoration must expose a draggable top area;
   unplugging must not itself reveal a hidden/minimized window.
3. Repeat at 100%, 150%, 200%, and mixed per-monitor DPI; change resolution/work area
   and primary display. Check a monitor gap, mostly hidden titlebar, taskbar overlap,
   huge saved size, and a work area smaller than the skin's minimum size.
4. Capture actual client/frame rectangles, available screen rectangles, DPI, states,
   and the INI before/after; preserve screenshots and native test output. Confirm
   the earlier taskbar-minimize fix remains intact. Do not mark these steps complete
   based on the synthetic rectangles or offscreen tests alone.
