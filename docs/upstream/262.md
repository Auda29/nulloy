Inspection at integration base `05c59cb`:

- `src/settings.cpp` defaults to local `Z`/`B` for Previous/Next and `Space` for
  Play/Pause. It initializes no `GlobalShortcuts/` defaults. There is no default
  binding of these actions to a media key, nor an initialized volume-key action
  shortcut. These are source findings, not packaged-settings runtime results.
- `src/actionManager.cpp` loads and saves customizable `Shortcuts/<action>` and
  `GlobalShortcuts/<action>`. Previous/Next connect to the real playlist slots;
  Play/Pause connects to `NPlayer::playPause`, not a generic backend toggle.
- `src/action.cpp` parses local QKeySequences into QAction shortcuts. Global
  sequences create QxtGlobalShortcut objects and route `activated` to `trigger`.
- `3rdParty/qxt-696423b-patched/qxtglobalshortcut_win.cpp:179-195` maps
  `Qt::Key_MediaNext`, `MediaPrevious`, `MediaPlay`, and `MediaStop` to Windows
  `VK_MEDIA_*`, including **MediaPlay -> VK_MEDIA_PLAY_PAUSE**. Volume Up/Down/Mute
  also have native keycode mappings. A mapping alone neither creates a player
  volume action nor proves headphone/system-volume semantics.
- The Windows switch has no `Qt::Key_MediaTogglePlayPause` case and falls back to
  zero for an unhandled key. Record the actual key emitted/captured by a device;
  do not assume the Qt enum `MediaPlay` and `MediaTogglePlayPause` are equivalent
  here. No speculative mapping patch is justified without a native reproduction.
- The same file receives `WM_HOTKEY` and invokes `activateShortcut`, while
  registration calls `RegisterHotKey`. That is a configurable hotkey path, not
  evidence of an OS media-session, Bluetooth AVRCP, or headphone integration.

## Finite native reproduction and acceptance procedure

1. Record OS/build, Nulloy version/commit and package hash, Qt version, skin,
   keyboard/headphone make/model, wired/USB/Bluetooth transport, driver, and
   exact shortcut settings. First test with a clean settings profile; save the
   original profile and restore it afterwards. Use three distinct tagged files
   with different visible titles and enough duration to avoid accidental EOS.
2. Confirm mouse Play/Pause/Next/Previous and default Space/B/Z work. Record
   loaded file/title, playlist position, and playback state before/after each
   operation. This separates a broken playback setup from missing key delivery.
3. With defaults untouched, press/release each physical Play/Pause, Next,
   Previous, Volume Up/Down/Mute button once: focused, unfocused with a text
   editor active, and minimized. Record all observations, including changes to
   **OS output volume versus Nulloy's own volume**. Lack of a default media
   binding is not itself proof that the configured hotkey path is broken.
4. In Keyboard settings capture the same physical keys as **local** shortcuts
   for the existing Play/Pause/Next/Previous actions, avoiding duplicate bindings.
   Save the displayed/serialized Qt sequences. Repeat focused delivery. A
   synthetic Qt event may be a supplemental control, never the device result.
5. Test **global** mappings separately (clear overlapping local/global mappings
   to avoid double activation). On Windows, capture native keycode/modifiers,
   `RegisterHotKey` result and `GetLastError` on failure, whether `WM_HOTKEY`
   arrives, and how many action activations result. Specifically distinguish
   `MediaPlay` from `MediaTogglePlayPause`. Test focused, unfocused and minimized.
   Repeat once after restart to check persistence/unregistration; avoid a soak.
6. For each configured successful key, require exactly one intended action per
   press: Play/Pause toggles state once; Next/Previous moves one file and updates
   its title/identity. Confirm text input is not unexpectedly consumed. Keep a
   failing device case alongside a working keyboard control. Repeat any failure
   with other media applications closed, then one known competing media app;
   record conflicts rather than assuming registration succeeded.
7. If the device works in another player but does not deliver a Qt/native hotkey
   to Nulloy, record the actual protocol/event route (for example an OS media
   command/session rather than WM_HOTKEY). Platform media-session work is a
   separate feature/design decision, not a stabilization patch to invent here.
   For non-Windows reporters, use that OS's native delivery path instead of
   treating Windows checks as acceptance.

Required evidence: package/settings identifiers, device/OS matrix, key enum and
native-event trace where available, before/after file/title/state/volume, exact
one-action counts, and failure details. Redact personal paths from public logs.
